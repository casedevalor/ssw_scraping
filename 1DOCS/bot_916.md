<h3># 📄 Routine 916</h3>

Automation for generating and uploading the report for routine **916** (manifest database — `BANCO_DE_DADOS_DO_MANIFESTO`) of the SSW system to SharePoint, always via screen 156.

---

## 📌 Objective

Run routine 916 for two periods (previous month + current month up to yesterday), routing each between an explicit error, screen 156, or an unexpected message.

---

## 📅 Business Rule (Dates)

The periods are decided in `_build_date_ranges()`:

| Condition | Periods processed | Function |
| --- | --- | --- |
| Day 2 onward | Previous month (full) **and** current month from the 1st up to **yesterday** | `Dates().previous_and_current_month_to_yesterday_ranges()` |
| Day 1 | Previous month (full) only — the current month has no closed day yet | same function |

No day/hour gate in the bot: the day-1 case is handled inside the `Dates()` method. Business rule (user, 2026-10-20): the current month **never includes today** — that is why 916 is **not** in the "always backfill last month" group (002, 036, 073, 076, 119, 200, 324, 411, 442, 452, 467 and 493), whose current month runs up to today.

Example: today 15/03/2025 → `[('010225', '280225'), ('010325', '140325')]`; today 01/03/2025 → `[('010225', '280225')]`.

Migrated on 2026-10-20 from the legacy architecture, which ran a single range — the 1st of the current month to yesterday (`calculate_day_initial_to_last_day()`, gone from `Dates()`); on day 1 that range was invalid (it ended before it started) and the previous month was never re-extracted. Each range produces one monthly file, named by its start date.

Each range is isolated — a failure in one does not stop the other — but if **every** range fails, `handler_download` raises `RuntimeError` so `main()`'s retry loop still engages.

## 🔁 Execution Flow

```mermaid
flowchart TD
    A[perform_login] --> B[Fill routine number + Tab]
    B --> C0{popup or #errormsglabel?}
    C0 -->|timeout 10s| Z1[TimeoutError]
    C0 -->|error| Z2[Log ERROR, abort attempt]
    C0 -->|popup| L[handler_download: for each date range]
    L -.->|every range failed| ZF[RuntimeError → main retries]
    L --> C["Fill dates"]
    C --> D[Click ►]
    D --> E{#errormsglabel appears?}
    E -->|timeout 60s| F1[TimeoutError → log ERROR, next range]
    E -->|"ERRO: " without "156"| F2[Log WARNING]
    E -->|"156"| F3[Open popup 156 → process_156_report: download, upload, check columns]
    E -->|other message| F4[RuntimeError → log ERROR, next range]
```

Opening the routine races the popup against the menu-level error label (`MSG_NOT_RELEASED`) instead of assuming the popup always opens.

The check is a mutually exclusive `if/elif/else` chain — it avoids the common bug of trying to click "Open 156" on a modal that the error handler already closed.

## ⚠️ Error Handling

| Scenario | Trigger | Action |
| --- | --- | --- |
| Timeout at the menu | Neither popup nor error within 10s | `TimeoutError`, attempt fails |
| Error opening the routine | `#errormsglabel` visible after `Tab` | Closes modal, logs `ERROR`, `RuntimeError` propagated |
| Timeout at the form | No message within 60s | `TimeoutError` for that range, logged `ERROR`, next range runs |
| `"ERRO: "` (without `"156"`) | Explicit system error | Logs `WARNING`, does not propagate |
| `"156"` | Report sent for asynchronous processing | Opens popup and delegates to `process_156_report` |
| Other message | Neither an error nor 156 | `RuntimeError` for that range, logged `ERROR`, next range runs |
| Every date range failed | Every `_process_date_range` call raised | `RuntimeError` "All N date range(s) failed" → attempt fails, `main()` retries |
| `"Opção não liberada"` (option not released) | `MSG_NOT_RELEASED` | Aborts the remaining attempts |

---

## 🔄 Resilience

- Up to **3 attempts** (`MAX_ATTEMPTS`), with `5s` between them.
- Standard multi-range loop: `handler_download` runs `_process_date_range` once per date range; a failure is logged as one `ERROR` line and the next date range still runs. The attempt only fails (and `main()` retries) when **every** date range failed.
- Aborts before the 3rd attempt if the message is `MSG_NOT_RELEASED`.
- Single cleanup at the end: `GarbageCollector` on `output/downloads/916/`, then the domain log upload, then the `Main routine completed.` line — always the last line of the run.

## 🛡️ Column Sentinel

Every downloaded file is checked against a fixed column baseline right after the upload. The result is **one line in the domain log**, which closes that file's block — it never raises and never affects the upload (see [column_sentinel.md](./column_sentinel.md)).

The file has **two header bands**, so it has two baselines, both checked against the same file — two sentinel lines per file:

| Baseline | Columns | Header | Band |
| --- | --- | --- | --- |
| `config/sentinel/916-MANIFESTO.yml` | 20 | line 2 | Manifest header (`1; sigla_manifesto; …`) — data lines start with `3` |
| `config/sentinel/916-CTRC.yml` | 14 | line 3 | CTRC header (`2; sigla_manifesto; …`) — data lines start with `4` |

Line 1 is a title (`0;<company>;BANCO_DE_DADOS_DO_MANIFESTO;<timestamp>`) and is not checked.

- **Where it runs:** `downloads.py → process_156_report`, right after the file is saved (`_handle_916`, no processor) and after the upload. `SENTINEL_BASELINES` in `downloads.py` maps `916` to both baseline names; no hook in the bot.
- **Processing before the check:** None — the raw SSW file is checked, exactly as it is uploaded.
- **Note:** Columns Q..T of the manifest header carry the report totals as `label: value` (`qtde_ctrc:  2077`, `tot_frete cif: …`, `tot_frete fob: …`, `tot_frete terc: …`). `916-MANIFESTO.yml` sets `label_separator: ':'`, so only the label is compared. Columns O..T of the CTRC header are empty (the file is 20 columns wide only because of the manifest header) and are ignored. Column A holds the band code (`'1'` / `'2'`), not a row counter. Checked against real files from 2023 to 2026 (VCS, NBL): both bands `OK`.

Log lines when the layout is intact:

```
SNTL - NBL SENTINEL 916-CTRC | 2026-10-NBL-916.csv | Columns: 14 found / 14 expected | OK
SNTL - NBL SENTINEL 916-MANIFESTO | 2026-10-NBL-916.csv | Columns: 20 found / 20 expected | OK
```

Any change shows up as `DRIFT` with `ADDED` / `REMOVED` / `RENAMED` / `MOVED` and the Excel column letter; a broken baseline shows up as `ERROR`.

## 📤 Output

- The actual download is handled by `process_156_report` (screen 156), once per range.
- File name: `<YYYY>-<MM>-<DOMAIN>-916.csv` (default branch of `_build_file_name`).
- SharePoint destination: `Banco_de_Dados/<DOMAIN>/916`
