<h3># 📄 Routine 019</h3>

Automation for extracting, downloading, and uploading the report for routine **019** of the SSW system to SharePoint, per unit.

---

## 📌 Objective

Run routine 019 once for each configured unit, with no date filter, routing to screen 156 when SSW queues the report, or downloading it directly otherwise.


---

## ⚙️ Business Parameter

No date range — this screen has no date fields. Units processed: `config.yml` → `variables.bot_019.list_units`, read via `settings.yaml_config.variables.bot_019.list_units`. Each unit is isolated — a failure in one does not stop the others.

A fresh popup opens for **every** unit (unlike routines such as 076 that reuse one popup for the whole list), so each popup is explicitly closed after use.

---

## 🔁 Execution Flow

```mermaid
flowchart TD
    A[perform_login] --> B[For each unit in list_units]
    B --> C[Fill unit + routine number]
    C --> D{popup or #errormsglabel?}
    D -->|timeout 10s| E1[Log ERROR, next unit]
    D -->|error only| E2["Filial não encontrada" — Log WARNING, next unit]
    D -->|popup| F1{Menu #errormsglabel also visible?}
    F1 -->|"Filial não encontrada"| E2
    F1 -->|no| F[handler_download]
    F --> G["Fill relatorio_excel = S, race download vs #errormsglabel, click ►"]
    G --> H{Which one wins within 60s?}
    H -->|neither| H0[Log ERROR, next unit]
    H -->|download| H1[Save .csv, upload to SharePoint, check columns]
    H -->|"156/processamento"| H2[Open popup 156 → process_156_report (uploads, then checks columns)]
    H -->|"no data" / "sigla não cadastrada" / unrecognized| H3[Log WARNING, click OK, next unit]
```

**Particularities of this routine:**

- On this screen, SSW can open the popup **and** show the menu-level `#errormsglabel` (e.g. `"Filial não encontrada."`) at the same time — the popup opening does not by itself mean the unit was accepted. `run()` gives the main page's error label a short grace check right after the popup resolves, before handing off to `handler_download`.
- `#errormsglabel` is a reused id: it shows menu-level errors on the main page, and a *different* set of messages inside the report popup once the format is submitted (`Não selecionou dados...`, `Sigla da unidade centralizadora não cadastrada.`, `Solicitação enviada para processamento...`).
- Inside `handler_download`, the download and the message modal are raced together (`task_download` vs `task_msg`, same pattern as `bot_435.py`) off a **single** click — this screen shows no message at all when the report is ready, so waiting for the message alone (then clicking again) would burn the full 60s timeout on every successful unit before the real download even started.

## ⚠️ Error Handling

| Scenario | Trigger | Action |
| --- | --- | --- |
| Timeout at the menu | Neither popup nor error within 10s | Logs `ERROR`, next unit |
| `"Filial não encontrada."` | Menu-level, checked on the main page even after the popup opens | Logs `WARNING`, closes the popup, next unit |
| `"Não selecionou dados para os parâmetros informados"` (no data for these parameters) | No data for this unit | Logs `WARNING`, next unit |
| `"Sigla da unidade centralizadora não cadastrada."` (centralizing unit sigla not registered) | Checked inside the report popup, same as the other submit-time messages | Logs `WARNING`, next unit |
| `"Solicitação enviada para processamento. Acompanhe sua execução pela opção 156."` | Report sent for asynchronous processing | Opens popup and delegates to `process_156_report` |
| Any other message | Text not recognized | Logs `WARNING`, dismissed with OK, next unit |
| Timeout | Neither the download nor a message appears within 60s | Logs `ERROR`, next unit |
| `"Opção não liberada"` (option not released) | `MSG_NOT_RELEASED` | Aborts the remaining attempts |

---

## 🔄 Resilience

- Up to **3 attempts** (`MAX_ATTEMPTS`), with `5s` between them.
- Aborts before the 3rd attempt if the message is `MSG_NOT_RELEASED`.
- Single cleanup at the end: `GarbageCollector` on `output/downloads/019/`, then the domain log upload, then the `Main routine completed.` line — always the last line of the run.

---

## 🛡️ Column Sentinel

Every downloaded file is checked against a fixed column baseline right after the upload. The result is **one line in the domain log**, which closes that file's block — it never raises and never affects the upload (see [column_sentinel.md](./column_sentinel.md)).

| Baseline | Columns | Header |
| --- | --- | --- |
| `config/sentinel/019.yml` | 30 | auto-detected |

- **Where it runs:** Direct download: `bot_019.py`, right after `download.save_as(...)`. Screen-156 path: `downloads.py → process_156_report`, which checks every routine that has a baseline.
- **Processing before the check:** None — the raw SSW file is checked, exactly as it is uploaded.
- **Note:** One file per unit → one sentinel line per unit in the log.

Log line when the layout is intact:

```
SNTL - RPV SENTINEL 019 | RPV-SJO-019.csv | Columns: 30 found / 30 expected | OK
```

Any change shows up as `DRIFT` with `ADDED` / `REMOVED` / `RENAMED` / `MOVED` and the Excel column letter; a broken baseline shows up as `ERROR`.

## 📤 Output

- File: `output/downloads/019/<DOMAIN>-<UNIT>-019.csv` (direct path) or produced by `process_156_report`'s `_handle_019` (screen 156 path) — same naming convention either way.
- SharePoint destination: `Banco_de_Dados/<DOMAIN>/019`
