<h3># 📄 Routine 103</h3>

Automation for extracting, processing, and uploading the report for routine **103** of the SSW system to SharePoint.

---

## 📌 Objective

Run routine 103 for three periods (last two months + current month), download the `.csv`, process it with `Dataframe_Analytics().processing_csv_103()`, and upload it to SharePoint.

---

## 📅 Business Rule (Dates)

| Periods processed | Function |
| --- | --- |
| Month before last, previous month, and current month up to today (3 ranges) | `Dates().last_three_months_ranges()` |

Each range is isolated — a failure in one does not stop the others.

## ⚠️ Error Handling

| Scenario | Trigger | Action |
| --- | --- | --- |
| Timeout at the menu | Neither popup nor error within 10s | `TimeoutError`, attempt fails |
| Timeout per range | Neither download nor message within 60s | `TimeoutError` → logged `ERROR` by the loop, next range |
| Download OK | `download` event | Processes via Pandas in a separate thread, uploads, checks columns, logs `INFO` |
| `"Nenhuma"` / `"Não existem cotações..."` (none / no quotations) | No data for the period | Logs `WARNING`, moves on |
| Any other message | `#errormsglabel` with unknown text | Dismissed with OK, `RuntimeError` → logged `ERROR` by the loop, next range |
| Exception in a range | e.g. `KeyError` in `processing_csv_103` | Logs `ERROR`, next range |
| Every date range failed | Every `_process_date_range` call raised | `RuntimeError` "All N date range(s) failed" → attempt fails, `main()` retries |
| `"Opção não liberada"` (option not released) | `MSG_NOT_RELEASED` | Aborts the remaining attempts |

---

## 🔄 Resilience

- Up to **3 attempts** (`MAX_ATTEMPTS`), with `5s` between them.
- Standard multi-range loop: `handler_download` runs `_process_date_range` once per date range; a failure is logged as one `ERROR` line and the next date range still runs. The attempt only fails (and `main()` retries) when **every** date range failed.
- Aborts before the 3rd attempt if the message is `MSG_NOT_RELEASED`.
- Single cleanup at the end: `GarbageCollector` on `output/downloads/103/`, then the domain log upload, then the `Main routine completed.` line — always the last line of the run.

## 🛡️ Column Sentinel

> ⚠️ **Dormant today.** `processing_csv_103` rewrites the file with exactly `config.yml → columns_103`, so the processed header always equals that list; a removed/renamed SSW column fails earlier with `KeyError`, and added/moved ones are dropped or reordered. So this check logs `OK` whatever SSW changes — it **validates nothing** while the routine is built this way. The baseline is kept ready (decided with the user on 2026-09-27) for when the fixed column list is replaced by another method; at that point it starts catching real changes with no code change.

Every downloaded file is checked against a fixed column baseline right after the upload. The result is **one line in the domain log**, which closes that file's block — it never raises and never affects the upload (see [column_sentinel.md](./column_sentinel.md)).

| Baseline | Columns | Header |
| --- | --- | --- |
| `config/sentinel/103.yml` | 47 | line 1 |

- **Where it runs:** `bot_103.py → _process_date_range`, right after `processing_csv_103`.
- **Processing before the check:** `processing_csv_103` keeps only `config.yml → variables.bot_103.columns_103`, in that order. The baseline must stay identical to that list (it starts with the SSW row counter `'1'`).
- **Note:** A column removed or renamed by SSW makes the processing fail with `KeyError` before the check (logged as a range failure); columns added or moved in the raw file are dropped/reordered by the processing and not flagged.

Log line when the layout is intact:

```
SNTL - TEC SENTINEL 103 | 2026-09-TEC-103.csv | Columns: 47 found / 47 expected | OK
```

Any change shows up as `DRIFT` with `ADDED` / `REMOVED` / `RENAMED` / `MOVED` and the Excel column letter; a broken baseline shows up as `ERROR`.
