<h3># 📄 Routine 306</h3>

Automation for extracting, downloading, and uploading the report for routine **306** of the SSW system to SharePoint, per fortnight.

---

## 📌 Objective

Run routine 306 for both fortnights of the configured period, handling direct download, secondary download (after confirmation), or routing to screen 156.

---

## 📅 Business Rule (Dates)

| Periods processed | Function |
| --- | --- |
| Both fortnights (1st and 2nd) | `_build_date_ranges()` → `Dates().previous_and_current_fortnight_ranges()` |

The file suffix (`-1` or `-2`) is decided by the start day (`01` → first fortnight).

---

## 🔁 Execution Flow

```mermaid
flowchart TD
    A[perform_login] --> B[Fill routine number + Tab]
    B --> C0{popup or #errormsglabel?}
    C0 -->|timeout 10s| H1[TimeoutError]
    C0 -->|error| H2[Log ERROR, abort attempt]
    C0 -->|popup| C[For each fortnight]
    C -.->|every range failed| ZF[RuntimeError → main retries]
    C --> D[Fill dates]
    D --> E[Click Excel]
    E --> F{download or #errormsglabel?}
    F -->|timeout 60s| G1[Log ERROR, next fortnight]
    F -->|download| G2[Save ROUTINE-N.csv, check columns, upload]
    F -->|"report generated successfully"| G3[Close modal, click Excel again, download, check columns, upload]
    F -->|"156"/"processing"| G4[Open popup 156 → process_156_report: download, check columns, upload]
    F -->|other message| G5[Log WARNING]
```

Opening the routine races the popup against the menu-level error label (`MSG_NOT_RELEASED`) instead of assuming the popup always opens.

## ⚠️ Error Handling

| Scenario | Trigger | Action |
| --- | --- | --- |
| Timeout at the menu | Neither popup nor error within 10s | `TimeoutError`, attempt fails |
| Error opening the routine | `#errormsglabel` visible after `Tab` | Closes modal, logs `ERROR`, `RuntimeError` propagated |
| Timeout per fortnight | Neither download nor message within 60s | `TimeoutError` → logged `ERROR` by the loop, next fortnight |
| Direct download | `download` event | Saves, checks columns, uploads, logs `INFO` |
| `"Relatório gerado com sucesso"` (report generated successfully) | Report ready for a second call | Closes modal, clicks Excel again, downloads, checks columns, uploads |
| `"156"` / `"processamento"` (processing) | Sent for asynchronous processing | Opens popup and delegates to `process_156_report` |
| Other message | Text not recognized | Closes modal, logs `WARNING` |
| Exception in a fortnight | e.g. the secondary download times out (120s) | Logs `ERROR`, next fortnight |
| Every date range failed | Every `_process_date_range` call raised | `RuntimeError` "All N date range(s) failed" → attempt fails, `main()` retries |
| `"Opção não liberada"` (option not released) | `MSG_NOT_RELEASED` | Aborts the remaining attempts |

---

## 🔄 Resilience

- Up to **3 attempts** (`MAX_ATTEMPTS`), with `5s` between them.
- Standard multi-range loop: `handler_download` runs `_process_date_range` once per date range; a failure is logged as one `ERROR` line and the next date range still runs. The attempt only fails (and `main()` retries) when **every** date range failed.
- Aborts before the 3rd attempt if the message is `MSG_NOT_RELEASED`.
- Single cleanup at the end: domain log upload + `GarbageCollector` on `output/downloads/306/`.

---

## 🛡️ Column Sentinel

Every downloaded file is checked against a fixed column baseline before the upload. The result is **one line in the domain log** — the upload always proceeds (see [column_sentinel.md](./column_sentinel.md)).

| Baseline | Columns | Header |
| --- | --- | --- |
| `config/sentinel/306.yml` | 14 | auto-detected |

- **Where it runs:** Direct and after-prompt downloads: `bot_306.py → _process_date_range`, right after `download.save_as(...)`. Screen-156 path: `downloads.py → process_156_report`, which checks every routine that has a baseline.
- **Processing before the check:** None — the raw SSW file is checked, exactly as it is uploaded (`_handle_306` has no processor).
- **Note:** One file per fortnight (`-1` / `-2`) → up to 2 sentinel lines per run; both are checked against the same `306.yml`.

Log line when the layout is intact:

```
INFO - TEC SENTINEL | 306 | 2026-09-TEC-306-1.csv | Columns: 14 found / 14 expected | OK
```

Any change shows up as `DRIFT` with `ADDED` / `REMOVED` / `RENAMED` / `MOVED` and the Excel column letter; a broken baseline shows up as `ERROR`.
