<h3># 📄 Routine 324</h3>

Automation for generating and uploading the report for routine **324** of the SSW system to SharePoint, always via screen 156.

---

## 📌 Objective

Run routine 324 for two periods (previous month + current month to date), trigger report generation for each, and delegate monitoring/download to screen 156.

---

## 📅 Business Rule (Dates)

The periods are decided in `_build_date_ranges()`:

| Condition | Periods processed | Function |
| --- | --- | --- |
| Always | Previous month (full) **and** current month up to today | `Dates().previous_and_current_month_ranges()` |

No day/hour gate: this routine belongs to the "always backfill last month" group (002, 036, 073, 076, 119, 200, 324, 411, 442, 452, 455ABH, 455CGK, 455F, 467 and 493), whose date helper is a one-to-one wrap of `Dates().previous_and_current_month_ranges()`.

Each range is isolated — a failure in one does not stop the other — but if **every** range fails, `handler_download` raises `RuntimeError` so `main()`'s retry loop still engages.

---

## 🔁 Execution Flow

```mermaid
flowchart TD
    A[perform_login] --> B[Fill routine number + Tab]
    B --> C{popup or #errormsglabel?}
    C -->|timeout 10s| E0[TimeoutError]
    C -->|error| D0[Log ERROR, abort attempt]
    C -->|popup| D[For each date range: fill dates]
    D --> G[Click Relatório]
    G --> E{#errormsglabel appears?}
    E -->|timeout 60s| F1[Log ERROR, next range]
    E -->|"156"/"processing"| F2[Open popup 156 → process_156_report: download, processing_sswweb_324, check columns on .xlsx, upload]
    E -->|other message| F3[Log WARNING, next range]
    D -.->|every range failed| F4[RuntimeError → retry]
```

Opening the routine races the popup against the menu-level error label (`MSG_NOT_RELEASED`) instead of assuming the popup always opens. This routine always routes via screen 156 for the actual report — there is no direct-download path on the main screen.

## ⚠️ Error Handling

| Scenario | Trigger | Action |
| --- | --- | --- |
| Timeout at the menu | Neither popup nor error within 10s | `TimeoutError`, attempt fails |
| Error opening the routine | `#errormsglabel` visible after `Tab` | Closes modal, logs `ERROR`, `RuntimeError` propagated |
| Timeout at the form | No message within 60s | `TimeoutError` for that range, logged `ERROR`, next range runs |
| `"156"` / `"processamento"` (processing) | Report sent for asynchronous processing | Opens popup and delegates to `process_156_report` |
| Other message | Text not recognized | Logs `WARNING` (does not propagate an error), next range runs |
| Every date range failed | Every `_process_date_range` call raised | `RuntimeError` "All N date range(s) failed" → attempt fails, `main()` retries |
| `"Opção não liberada"` (option not released) | `MSG_NOT_RELEASED` | Aborts the remaining attempts |

---

## 🔄 Resilience

- Up to **3 attempts** (`MAX_ATTEMPTS`), with `5s` between them.
- Standard multi-range loop: `handler_download` runs `_process_date_range` once per date range; a failure is logged as one `ERROR` line and the next date range still runs. The attempt only fails (and `main()` retries) when **every** date range failed.
- Aborts before the 3rd attempt if the message is `MSG_NOT_RELEASED`.
- Single cleanup at the end: domain log upload + `GarbageCollector` on `output/downloads/324/`.

## 🛡️ Column Sentinel

> ⚠️ **Dormant today.** The header is built by `processing_sswweb_324` itself (hard-coded names), not read from SSW. So this check logs `OK` whatever SSW changes — it **validates nothing** while the routine is built this way. The baseline is kept ready (decided with the user on 2026-09-27) for when the processing stops hard-coding the column names; at that point it starts catching real changes with no code change.

Every downloaded file is checked against a fixed column baseline before the upload. The result is **one line in the domain log** — the upload always proceeds (see [column_sentinel.md](./column_sentinel.md)).

| Baseline | Columns | Header |
| --- | --- | --- |
| `config/sentinel/324.yml` | 7 | line 1 (first row of the `.xlsx`) |

- **Where it runs:** `downloads.py → process_156_report`, right after `processing_sswweb_324` (on the `.xlsx`) — covered automatically because the baseline exists.
- **Processing before the check:** `processing_sswweb_324` parses the `.sswweb` text with a regex and writes an `.xlsx` with 7 **hard-coded** column names; the check reads that `.xlsx`.
- **Note:** What can really break today is invisible to it: shifted slices / a regex that stops matching produce wrong or empty data under a perfect header. A check inside the processing (e.g. `WARNING` on 0 extracted rows) would be the fitting guard for that.

Log line when the layout is intact:

```
INFO - TEC SENTINEL | 324 | 2026-09-TEC-324.xlsx | Columns: 7 found / 7 expected | OK
```

Any change shows up as `DRIFT` with `ADDED` / `REMOVED` / `RENAMED` / `MOVED` and the Excel column letter; a broken baseline shows up as `ERROR`.
